# 按次计费模型优化（dsh-per-request-billing）

DeepSeek Harness（DSH）插件：把**按请求次数计费**的模型（通常是包月或按次计费的第三方中转 / 订阅）标记出来，并在用到它们时自动把调用方式往「更少请求、更长上下文」上引导。

一条底线贯穿始终：**减少请求次数绝不意味着跳过授权与审批**。

## 引言

按 token 计费的模型，省钱的办法是少读少写；按**次数**计费的模型正相反——每一次往返都是固定成本，跟这次往返里带了多少 token 无关。同一个任务，拆成 20 次小请求和压成 4 次大请求，账单能差五倍。

麻烦在于两件事都没有现成开关：一是「哪些模型是按次计费的」只在你脑子里，运行时并不知道；二是就算知道了，模型自己也不会因此改变习惯——它照样一个文件读一次、一步只发一个工具调用。

本插件把「按次计费」变成可持久化的标记（全局 / 提供方 / 单模型三级），再让标记在每一次组装系统提示词时生效，把调用纪律直接写进提示词。

## 功能

- **三级「按次计费」标记**，优先级从高到低：单模型 → 提供方（其下所有模型继承）→ 全局（所有模型默认按次计费）
- **每一级都能显式设为「按量计费」**，所以单个模型可以退出被标记的提供方
- **标记持久化**：写在 profile 的 settings 文档里，重启后仍在
- **模型清单自动读取**：从运行时取每个提供方实际配置的模型，新增提供方或加模型后自动出现；配置里还没有的模型可以手动输入 id 加入
- **两个 UI 入口**：设置面板的「按次计费」整页，以及**模型配置页每个提供方卡片内**的勾选区（就在你配 API Key / 模型的那张卡片里）
- **每步组装时注入调用纪律**（仅命中按次计费模型时）：批量与并行调用工具、一次拿全量、复用已有结果、一个回合内完成索取-修改-验证、主动利用更长上下文、交付完整结果
- **工具描述优化**：命中时给 `bash` / `pwsh` 的本次组装追加批量执行引导
- **模型可调用的工具**：`billing_status` 查询、`billing_set` 切换（持久化），所以也可以直接说「把 xx 提供方设成按次计费」

## 安装

**从 GitHub 安装**（仓库存有构建产物 `lib/`，不需要现场构建）：

```bash
dsh plugin --profile web add github:increChong/dsh-per-request-billing-plugin
dsh web   # 重启 web 服务使 profile 生效
```

**本地安装**：

```bash
git clone https://github.com/increChong/dsh-per-request-billing-plugin.git
dsh plugin --profile web add /path/to/dsh-per-request-billing-plugin
dsh web
```

**从 tarball 安装**：

```bash
npm pack && dsh plugin --profile web add ./dsh-per-request-billing-0.1.0.tgz
```

`dsh plugin` 是 pnpm 的转发器，因此 path / git / tarball 都能装，不必先发 npm。安装后声明了 `dsh.bundle` 的依赖会被自动登记为 profile 的 bundle 层，不用手工编辑任何文件。

改动 `src/client/index.js` 后需要 `npm run build` 重新生成 `lib/client.js`。

## 卸载

```bash
dsh plugin --profile web remove dsh-per-request-billing
```

## 使用

打开 **设置 → 按次计费**：

- 顶部一行是全局开关与统计（已标记模型数 / 已注入优化提示词的步骤数）
- 每个提供方一张卡片：提供方级总开关 + 该提供方所有模型的勾选芯片
- 芯片上标注 `单独设置`（自己覆盖）或 `· 继承`（跟随提供方）；勾选的显示为告警色
- 在提供方被标记时单独取消某个模型，会为该模型写入一条「按量计费」覆盖，它从此不再被优化
- 底部有「清除单模型勾选」按钮（清掉所有 `单独设置` 的模型覆盖，不碰提供方与全局开关），以及手动输入模型 id 的输入框

**模型配置页 → 任意提供方卡片内**：同一套开关，位置更贴近你的配置动作。

也可以直接让模型操作：

```
billing_status                                                  # 看当前标记与判定情况
billing_set  scope=provider  provider=xxx  on=true             # 整个提供方按次计费
billing_set  scope=model     provider=xxx  model=yyy  on=true   # 只标记某个模型
billing_set  scope=model     provider=xxx  model=yyy  on=false  # 让某个模型退出
```

`on=false` 写入的是**显式的按量计费覆盖**，优先级高于提供方与全局开关——所以它能真正把某个模型从按次计费的提供方里摘出来。

勾选后**从下一个模型步骤开始生效**。

## 工作原理

### 标记与优先级

每个「提供方 / 模型」组合解析出一个模式，`per-request`（按次计费）或 `per-token`（按量计费）：

```
单模型显式设置  →  提供方设置  →  全局开关  →  默认 per-token
```

任一级都可以显式指定 `per-token`，因此「提供方整体按次计费、个别便宜模型按量计费」这类组合可以精确表达。

### 判定当前模型

每次组装系统提示词时，插件判定**本步实际生效的路由**。会话中途切换模型会立即反映，不会停留在会话建立时的选择上；只有当实时信息缺失时，才逐级回退到本会话已选或最近一次使用的路由，最后才退到会话起点默认。判定只针对解析出的那一个路由，未标记的模型原样返回，不做任何修改。

### 注入什么

命中按次计费模型时，往系统提示词追加一节调用纪律，核心是「用尽可能少的请求次数完成同样的工作」：

1. 先侦察、后行动，一次调用批量收集信息
2. 并行发起互不依赖的工具调用，而不是串行地一次发一个
3. 一次拿全量，宁可单次输出更长，也不为省 token 多跑一轮
4. 复用同一轮内已获得的结果，不重复读取或执行
5. 一个回合内完成索取、修改与验证，不用多轮小请求逐步试探
6. 主动利用更长上下文；只在真的触达上限时才压缩
7. 交付完整结果（结论、关键证据、后续建议）

同一节里写明**安全底线，优先级高于以上任何一条**：需要批准的操作照常发起批准流程，不得把多个需要分别授权的动作合并成一个来绕过审批，不得为少一轮而省略必要校验。优化只作用于「调用方式」，不改变「是否被允许」。

### 工具描述优化

命中时，本次组装里 `bash` / `pwsh` 的工具描述会追加一段批量执行引导（用 `&&` 合并命令、一次脚本完成多步、同步内并行发起互不依赖的调用）。这只影响当前这一次组装，不会改动工具注册表，也不影响其他 agent。

### 生效范围与数据

- 标记保存在 profile 的 settings 文档中，通过 DSH 的 `settings` 服务读写
- 注入的提示词与工具描述只作用于当前模型请求
- 不触碰 `approval`、沙箱或权限行；不改写任何适配器的 `contextWindow`

## 已知限制

- **「增加上下文长度」是提示词引导，不是改配置。** 上下文窗口由各适配器自己的 `contextWindow` 决定，插件不会去改写它；这里做的是让模型主动把更多内容放进单次请求、不提前触发压缩。
- **审批策略不变。** 插件只改提示词与工具描述，不触碰 `approval`、沙箱或权限行。
- **只影响被标记的模型。** 判定只针对本步生效的路由；未标记的模型原样返回，不追加任何内容。
- **提供方卡片内嵌 UI 只覆盖官方两个适配器族**（`llm-pi-ai` 与 `llm-deepseek`）。第三方适配器族仍可在**设置 → 按次计费**整页里配置，只是不会出现在它的提供方卡片里。
- **模型判定依赖运行时的会话状态接口。** 上游若变更这些接口，最坏结果是插件静默不再注入优化提示词（不会破坏模型步骤）。
- **浏览器端渲染需自行确认。** 客户端 bundle 由 Web 模块图加载，座位渲染依赖 profile 里存在模型配置页。

## 数据与隐私

- 标记（全局开关、提供方级默认、单模型覆盖）保存在 profile 的 **settings 文档**中，通过 DSH 的 `settings` 服务读写，不额外落盘、不联网。
- 插件的 HTTP 路由挂在 DSH WebServer 上，只服务两个 JSON 读写；它不读文件、不读凭据、不发起任何出站请求。与其它 WebServer 路由一样，**不要把 DSH 的 WebServer 暴露到公网**。
- 注入的提示词与工具描述只作用于当前模型请求，不写入任何外部系统。
